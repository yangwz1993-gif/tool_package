# 附录 · 踩过的坑

按踩到的顺序记，每条都写成「现象 → 原因 → 怎么办」。

## 一、herdr 客户端根本附着不上，二维码链接被裁

**现象**：前台 Ghostty 里那个 herdr 会话看起来开着，但 `pane read` 只能拿到 40 行、8.6 万个字符之外的内容全看不见。授权二维码正好 47 行，下面那行 `alternatively open: <链接>` 被裁掉，你只能靠肉眼扫屏。

**原因**：herdr 默认**拒绝嵌套运行**。启动它的 shell 本身就在某个 herdr 会话里（比如从 Discord 那条链路发起的命令），`HERDR_ENV` 之类的变量被继承，herdr 启动时报

```
error: nested herdr is disabled by default.
"recursion is a pathway to many abilities some consider to be... unnatural."
```

然后退出。**没有客户端附着时，herdr 用 80×40 的默认尺寸渲染 panes**，内容超出就裁。

**怎么办**：用 `scripts/herdr-lark-launch.sh`，它先清掉所有 `HERDR_*` 再 `exec herdr`。附着上之后 pane 从 40 行变成 46 行，链接就露出来了。

排查命令：

```bash
ps -eo command | grep -E "[h]erdr --session lark-local$"
```

有输出才算附着上了。

## 二、白名单为空时，消息被静默拒绝

**现象**：飞书里发了消息，机器人毫无反应，看不出是没收到还是被拒了。

**原因**：`Allowlisted users` 为 0 时，机器人会拒绝并回一条带授权码的提示。而**未授权的消息不会生成对话分屏**，所以本机也看不到任何动静。

**怎么办**：看 `/lark-bot` 的输出。`Chats` 涨了但 `Allowlisted users` 还是 0，就是卡在白名单。执行 `/lark-bot allow`，它会列出最近被拒的发送者让你选。

## 三、机器人把别的会话的记忆认领成了自己的

**现象**：在飞书里发了一句没头没尾的「啥意思」，机器人回了一大段风骚律师字幕对齐的汇报，还以第一人称说「你上一条是我的 E09 字幕修正汇报」——而那个会话里根本没有这条消息。

**原因**：飞书那边的 pi 会话是全新的，只有这一条用户消息。它拿不到上下文，于是**去硬盘上翻找**——先搜 context-mode 知识库（无结果），再列目录，最后读了 `~/.pi/agent/sessions/--Users-yangwz-Documents-workspace--/` 下另一个 41 MB 的会话文件（那是 Discord 那条链路的记录），把里面的内容当成了自己的经历。

**这是模型的行为选择，不是配置问题。** 给它加「你在飞书」的环境说明也没用——知道自己在哪个渠道，并不能阻止它去读别的会话文件。

**怎么办**：给它的话带上事由，别发无上下文的三字短语。要**清空**这个会话用 `/reset`（破坏性）；要**另开一个**干净会话用 `/new`，原来的历史留着（见 [`03-多会话.md`](03-多会话.md)）。

顺带记住这个**能力边界**：飞书机器人有权读写整个文件系统，也就包括你**所有** pi 会话的记录。所以白名单别加别人。

## 四、`PI_DISCORD_EXTENSION` 漏进飞书 worker（无害但要清）

**现象**：翻飞书 worker 的环境变量，能看到 `PI_DISCORD_EXTENSION` 指向 Discord 桥的扩展。

**原因**：pi-lark-bot 的 `panes.ts` 把监听进程的**整个 `process.env`** 原样复制给每个 worker，只清理 `PI_SUBAGENT_*`、`PI_LARK_BOT_*`、`PI_SESSION_ID`、`PI_SESSION_FILE` 四类。而监听进程的环境是从启动它的 shell 继承的，一路带着 Discord 的东西。

**实际影响：没有。** 全机器只有一处读这个变量——Discord 桥自己的启动器 `herdr-discord/upstream/src/herdr.js`，它在拉起 pi 面板时追加 `--extension`。而飞书 worker 的 pi 由 pi-lark-bot 拉起，参数固定是 `["--session", <file>, "-e", <worker-extension>]`，只挂一个扩展。所以它是**悬空的死变量**。就算真被加载也不会出事，`discord-output.ts` 自己会先查 pane 是否在 Discord 的映射表里，不在就什么都不做。

**怎么办**：`scripts/herdr-lark-launch.sh` 顺手清掉了。属于卫生问题。

## 五、`pi update --extensions` 会冲掉本地改动

**现象**：某次更新之后，我们自己加的功能凭空消失。

**原因**：pi-lark-bot 装在 `~/.pi/agent/git/github.com/fyang93/pi-lark-bot`，是 `pi install` 拉的 git 副本，更新时按上游覆盖。

**怎么办**：改动同时以两种形式留在本仓库——`source/` 里的完整源码，和 `extensions/pi-lark-bridge.patch` 里的差异。恢复用 `git apply`，或者 `./scripts/deploy.sh --go` 直接覆盖回去（部署完会自动重新导出 patch，所以 patch 不会过期）。

## 六、机器人不能主动给用户发消息

**现象**：

```
code 230101: Sending messages to users is temporarily unavailable.
```

**原因**：回复（reply 接口）是通的，**主动发起新会话**不行。多数情况下和应用发布状态或可用范围有关。

**怎么办**：暂时不影响使用，回复和表情都不受牵连。将来要做主动推送再单独解决。

## 七、机器人在会话列表里找不到

**现象**：应用建好了，但飞书的会话列表里没有它。

**原因**：飞书的机器人**不会自动出现在会话列表**——和群不一样，它必须有会话才进列表。没人跟它说过话之前，它在列表里根本不存在。

**怎么办**：用顶部**搜索框**搜应用名，或者去「工作台」找。搜不到才说明应用没发布或可用范围没覆盖到你。

> 扯远一句：应用名是飞书按账号自动生成的，形如 `<你的显示名>的智能助手`。想改去开发者后台改。

## 八、类型检查和测试，必须跑

**现象**：一开始以为「本地没装 tsc，类型检查跑不了」，靠运行时验证就够了——`npm run typecheck` 起不来，`npx typescript` 也报 `could not determine executable to run`。

**这个判断是错的，而且真的付出过代价**：表情回应那 26 行改动里，`ACK_EMOJI` 常量的那条 edit 被工具拒绝了，没人发现；部署后每次收信都在那一行抛 `ReferenceError`，消息照收、回复一条没有，界面上只有一句不带细节的笼统错误（详见 [`02-表情回应.md`](02-表情回应.md)）。这种错 `tsc` 一句话就能指出来。

**怎么办**：`source/package.json` 里本来就有 devDependencies（`typescript`、`tsx`）和 `test`/`typecheck` 两个脚本，只是从没装过。在 `source/` 里 `npm install` 一次即可，本地 3 秒就装好。

现在有闸门了：

```bash
cd pi-lark-bridge
./scripts/check.sh          # tsc --noEmit + 全部单元测试
./scripts/deploy.sh --go    # 部署前默认先跑 check.sh，不过就不部署
```

## 九、`rsync -n` 不带 `-v`，dry-run 会假装「没有差异」

**现象**：`./deploy.sh` 的 dry-run 里「### 同步 src/ ###」下面一片空白，看起来像源码和安装位置完全一致——但两边其实差着五个文件。

**原因**：macOS 自带的是 `openrsync`（自称 `rsync version 2.6.9 compatible`）。它只有在 `-v`（或 `-i`）下才输出文件列表，光 `-n` 什么都不打印。「没输出」被理所当然地读成了「没差异」，还写进了当时的汇报里。

**怎么办**：`deploy.sh` 的 dry-run 改成 `-n -i`，列出每个会变的文件和它的变更标记：

```
>f.st.... controller.ts
```

同类教训：一个工具「沉默」，不等于「没事」。要区分「真没差异」和「它根本没说」，用 `diff -rq` 或 `rsync -i` 亲自看一眼。

## 十、规则死了：改了 `/new` 的语义

**现象**：上游 `/new` 是「删掉历史重来」，我们把它改成了「再开一个新会话」，破坏性行为改名成 `/reset`。

**为什么必须改**：「新建对话」和「清空对话」是两件事。想要多会话，就必须有一个不破坏历史的建新会话的命令；而把两者合并在一个命令里，迟早误删。

**代价**：读上游文档、或者未来上游自己改了 `/new` 时，这里会有语义冲突。所以：文档里写清楚（[`03-多会话.md`](03-多会话.md)）、命令回复里写清楚（`/new` 的回消息会说明旧会话没被关闭）、单元测试盯住（`test/commands.test.ts` 里断言 `/reset` 只落在当前会话上）。
