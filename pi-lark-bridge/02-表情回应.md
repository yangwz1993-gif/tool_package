# 02 · 表情回应（收到消息立刻贴 ✅）

## 要解决什么

从飞书发一条消息出去，到 pi 真正开始回话，中间有一段时间是静默的。你没法判断消息是**送进去了**还是**卡在哪了**。这个改动在消息通过鉴权的那一刻，立刻在你那条消息上贴一个 ✅，不用等模型开口。

## 上游没有这个功能

pi-lark-bot 的源码和 README 里 `reaction` / `emoji` 是**零匹配**的。这是本项目自己加的，改动一共 26 行，落在三个文件：

- `source/src/types.ts` — 在 `BotTransport` 接口上加可选的 `react?(messageId, emoji)`
- `source/src/lark.ts` — 实现 `react()`，调 `client.im.v1.messageReaction.create`
- `source/src/controller.ts` — 在授权通过之后、交给 pi 之前调用它

完整 diff 存在 [`extensions/ack-reaction.patch`](extensions/ack-reaction.patch)，基线 commit 记在 `extensions/ack-reaction.based-on.txt`。

## 需要单独申请的权限

这个接口不在 `link` 默认申请的那批里，要另外批一次：

```
im:message.reactions:write_only
```

申请链接：

```
https://open.feishu.cn/app/<APP_ID>/auth?q=im:message,im:message.reactions:write_only&op_from=openapi&token_type=tenant
```

没开的话接口会返回 `99991672`，而**代码会静默跳过**（见下面「设计决定」第二条），表现就是「消息能回、但没表情」。

## 两个刻意的设计决定

**一、只在鉴权通过之后贴。** 插入点在 `controller.ts` 的收信流程里，`isAllowed()` 判定通过之后、交给 pi 之前：

```ts
if (!await this.isAllowed(message)) {
  // ……未授权：发拒绝提示并 return，这里不会走到
}
if (!this.active) return;
// 授权通过，贴 ✅
void this.options.transport.react?.(message.id, ACK_EMOJI);
this.chats.set(key, { ... });
```

未授权的发送者**不会**先看到一个 ✅ 再被拒绝——那反而误导，让人以为消息被受理了。

**二、它是「发了就不管」且永不抛错。** `react()` 内部把异常全吞掉：

```ts
async react(messageId: string, emoji: string): Promise<void> {
  try {
    await this.request(() => this.client.im.v1.messageReaction.create({ ... }));
  } catch (error) {
    this.report("Lark acknowledgement reaction failed");
  }
}
```

调用点也是 fire-and-forget（`void ...`，不 await）。理由是表情纯属装饰：权限被撤、消息被撤回、接口临时抽风，**都不允许拖慢或弄丢真正的回复**。这条写进了 `types.ts` 的接口注释里当契约。

`ACK_EMOJI` 常量在 `controller.ts` 顶部，值是 `"OK"`，在飞书里渲染成 ✅。

## 踩过的坑：常量没定义，所有回复一起消失

第一版这段改动上线后，每次收信都在那一行抛 `ReferenceError: ACK_EMOJI is not defined`。症状极具误导性，值得单独记一笔：

- 消息**能收进来**（`seen.json` 里都有，`/lark-bot` 的 `Chats` 也有可能涨）
- ✅ **贴不出来**（这一行根本没执行到）
- 回复**一条都没有**（异常发生在交给 pi 之前，整条 `run()` 直接中断）
- 界面上只留一句**不带细节**的 `Error: Lark bot operation failed. Check connectivity, app permissions and the session pane.`

最后一句是 `index.ts` 的 `onError` 故意为之：它只对少数白名单前缀附上原始信息（怕把 SDK 错误和凭据带出来）。`ReferenceError` 不在白名单里，所以现场只剩一句笼统的话，指向的还全是错的方向（网络？权限？）。

两处一起改掉了：

- `controller.ts` 里补上常量定义；`void ...react?.(...)?.catch(this.onError)` 再加一层兜底，保证任何 transport 都不可能把未处理的 rejection 顶出来
- 加 `scripts/check.sh`（`tsc --noEmit` + 单元测试），`deploy.sh` 部署前默认先跑它 —— 这个错 `tsc` 一眼就能抓到
- `test/ack-reaction.test.ts` 盯住「消息被贴了 `OK`、回复照旧送到」这条链路

## 部署与验证

```bash
cd pi-lark-bridge
./scripts/check.sh           # 类型检查 + 单元测试（部署前的闸门）
./scripts/deploy.sh          # 看 dry-run
./scripts/deploy.sh --go     # 同步到 pi 的安装位置（会先跑一遍 check.sh）
```

然后重启监听（**顺序不能省**）：

```
/lark-bot off
/reload
/lark-bot on
```

`on` 时会再弹一次远程执行确认框，正常。

验证：在飞书里发一句话，看那条消息旁边有没有立刻出现 ✅。

### 如果贴不出来

按这个顺序查：

- 先看 `/lark-bot` 输出的 `Chats` 有没有涨 —— 没涨说明消息根本没到
- `Allowlisted users` 是 0 的话先放行，未授权不会贴表情
- 用「假 message_id 探测法」（见 [`01-环境连接.md`](01-环境连接.md) 第二节）确认权限真的开通了
- 都正常，那就是 `/reload` 没重新读盘上的源码 —— 把面板里的 pi 整个重启一次，别只 reload

## 上游更新后怎么恢复

`pi update --extensions` 会把安装位置重置成上游版本，我们的改动就没了。恢复：

```bash
cd ~/.pi/agent/git/github.com/fyang93/pi-lark-bot
git apply /path/to/pi-lark-bridge/extensions/pi-lark-bridge.patch
```

patch 是 `deploy.sh --go` 每次自动重新导出的（对着 `extensions/based-on.txt` 里那个 commit 生成），所以它永远等于安装位置里那份**已经通过检查**的代码。上游改动大时可能需要手工合并；更省事的做法是直接用本目录的 `source/` 覆盖回去：`./scripts/deploy.sh --go`。
